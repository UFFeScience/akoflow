## What Montage does for astronomy

A sky survey records many images rather than a single photograph of an entire region. Those images may use different pixel grids and have different background levels. Simply placing them next to each other would leave misalignment and visible seams.

[Montage, developed at IPAC](https://www.ipac.caltech.edu/project/montage), combines astronomical images while preserving positional and calibration fidelity. Its building blocks operate on FITS files, the scientific image products in this workflow. The color PNG is a visualization of the resulting mosaics; retain the FITS products for scientific analysis.

Three operations explain much of the computation:

- **Reprojection:** map observations onto a common output grid. The [mProject documentation](https://irsa.ipac.caltech.edu/Montage/docs/mProject.html) describes the input image, header template, reprojected image, and accompanying area image.
- **Background matching:** measure overlap differences and solve for consistent corrections. [mBgModel](https://irsa.ipac.caltech.edu/Montage/docs/mBgModel.html) uses the fitted differences to estimate a global set of adjustments.
- **Coaddition:** combine corrected observations into mosaics. The [Montage module guide](https://irsa.ipac.caltech.edu/Montage/docs/how.html) describes the tools for metadata generation, reprojection, background correction, and mosaicking.

Here, twelve input FITS observations feed three image-band branches. Each branch produces a FITS mosaic and a monochrome preview; a final activity combines the three mosaics into the color preview.

Independent projections and overlap operations can run concurrently after their own inputs are ready. Background modeling introduces a convergence point within each band. The final color preview waits for its three mosaic inputs. There is no extra global barrier forcing an unrelated band to wait at every stage.

This is why the DAG matters: it encodes scientific dependencies. A scheduler can choose where ready work runs, but cannot skip an input merely to make the graph appear more parallel. The [Montage parallelization guide](https://irsa.ipac.caltech.edu/Montage/docs/grid.html) explains the relationship between independent image operations and background-model convergence.

## Reproduce the workload locally

If this is your first AkôFlow experiment, begin with [the Desktop walkthrough](/blog/from-a-dag-to-your-first-run). It teaches definitions, environments, scopes, plans, and runs with a tiny local workload.

The full Montage bundle adds a command-line preparation and execution path. Have **Git, Go 1.23 or newer, and Docker with linux/amd64 support** available. Keep at least **15 GiB** of free disk for the image and intermediate workspaces. Retention and concurrency affect the peak requirement. Apple Silicon runs this amd64 workload through emulation and may take substantially longer.

### 1. Get the versioned example

```bash
git clone https://github.com/UFFeScience/akoflow-examples.git
cd akoflow-examples
git checkout --detach d890c3171e3661890305b763b8fc3ede48bb61b4
cd scientific-workflows/montage-050
```

Pinning the checkout makes this walkthrough refer to a specific example revision. The [bundle README](https://github.com/UFFeScience/akoflow-examples/blob/d890c3171e3661890305b763b8fc3ede48bb61b4/scientific-workflows/montage-050/README.md) documents its requirements and commands.

The bundle contains `workflow.yaml`, `environment.yaml`, `scope.yaml`, and `topology.yaml`, plus preparation, execution, and validation scripts. The workflow retains historical simulation durations as model inputs. Use the provided runner or daemon helper for the real workload; importing that source YAML alone is not the complete real-execution setup.

### 2. Prepare the image and inputs

```bash
./prepare.sh
```

Preparation obtains the pinned image and Go dependencies, and checks the command/input contract. The image includes approximately 87 MiB of source FITS data, region headers, lookup tables, and the native Montage tools. There is no need to locate twelve observations manually.

The upstream image is pinned by digest:

```text
ovvesley/akoflow-wf-montage@sha256:26b060b83b990557ea86ab40503cc8f17ab6016b5973e7e6f9201100a96440c9
```

Preparation success establishes that the inputs and commands are available. It does not mean all scientific activities have executed.

### 3. Execute the complete local DAG

```bash
./run.sh
```

The standalone runner uses **two CPU slots** by default. Each activity becomes eligible once its dependencies finish and a slot is available. It copies the bundled input seed, executes the native commands with network access disabled, and writes activity observations under `outputs/`.

This path provisions no cloud machines and needs no remote HPC account. It is a substantial scientific workload: allow it to finish rather than interpreting a slow projection as a completed run.

### 4. Validate and open the products

```bash
./validate.sh
```

Inspect the final files in `outputs/`:

| Product                                           | What it gives you                       |
| ------------------------------------------------- | --------------------------------------- |
| `1-mosaic.fits`, `2-mosaic.fits`, `3-mosaic.fits` | Three 1800 × 1800 scientific mosaics    |
| `1-mosaic.png`, `2-mosaic.png`, `3-mosaic.png`    | Monochrome visual previews              |
| `mosaic-color.png`                                | Combined color preview                  |
| `manifest.json`                                   | Generated artifacts and SHA-256 digests |
| `dag-validation.json`                             | Dependency-wave validation              |
| `stage-<activity>.json`                           | Per-activity observations               |

The validator checks all 58 activity records, FITS dimensions, and PNG headers. A successful manifest is published only after the workflow and final-file checks pass. Merely finding one intermediate image is insufficient to declare the experiment complete.

### Inspect a daemon-managed run in Desktop

The bundle also supports a daemon helper that registers the local environment, builds the declared image, and submits the 58 activities to the engine. This advanced path requires a daemon whose API address and token you manage; follow [API connection setup](/docs/tutorials/api-access). The graphical Desktop installation keeps its internal credentials managed by its proxy—do not assume that it exposes a shell token.

From the example directory, with that daemon connection configured:

```bash
go run ../../tools/daemon-local -root ../.. -example scientific-workflows/montage-050 -wait=false
```

The command prints the submitted run ID and returns while execution continues. Connect Desktop to that same instance and open the run. Inspect its activity DAG, file handoffs, logs, and completion status. The daemon owns execution and transfers; the standalone runner's `outputs/` directory belongs to the separate standalone path.

The real API-reported makespan was about **1.91× the planned estimate**. That is an observation from this run, not a general slowdown factor. Close agreement between the plan and simulation did not establish that the real distributed execution would match either prediction.

The accompanying results record identifies whole-workspace traffic and different planned edge volumes as a comparability limit. Summed transfer or compute work can overlap across activities and is not the same as wall-clock makespan. Likewise, a zero reported interference value cannot establish that physical contention was absent.

The recorded cloud compute-and-boot-disk lifecycle estimate was **USD 0.3532** at the experiment's list rates. It excludes network egress, public IPv4, reusable image storage, discounts, and tax, and assigns no calibrated monetary tariff to HPC. It is an estimate, not a provider invoice or a current price quote. Other cost fields in the JSON use different task/window scopes and should not be treated as equivalent bills.

## What is—and is not—verified for the local bundle

The checked-in local image contract was validated on **2026-10-20**: twelve FITS inputs, 58 activities, and 138 named handoffs. That record explicitly states `fullExecutionPerformed: false`. Its separate daemon snapshot recorded a running workflow with zero completed activities at capture time. These are historical snapshots; neither establishes the current state of another instance.

The completed hybrid run supplies the mosaic and the results in this article. To claim a completed reproduction on your machine, retain your own successful validator output, activity records, and output manifest. The [local showcase page](/docs/showcase/scientific-workflows/montage-050) links the checked-in contract and daemon evidence.

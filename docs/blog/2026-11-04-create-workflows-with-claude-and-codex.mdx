**Starting with version 1.0.12, AkôFlow includes MCP integration to connect AI apps such as Claude and Codex directly to its workflow engine.** You can now describe an experiment in a conversation and ask your assistant to create workflow definitions, prepare execution plans, start runs and inspect their results through AkôFlow tools.

MCP—Model Context Protocol—provides that connection. The assistant works with the same persisted definitions, plans and runs that you see in Desktop, using the permissions you grant to its connection. The [1.0.12 release](/docs/changelog) brings managed app connections, native client setup, connection verification, credential rotation and revocation.

This tutorial takes that connection from setup to a result you can inspect: three activities turn the measurements **2, 4 and 6** into a report containing **`Mean: 4.00`**. You will connect your AI app, give it focused prompts, inspect the saved DAG, and execute the workflow on a local Docker runtime.

## What you need

- [AkôFlow Desktop and its matching runtime](/docs/installation), open and showing **Connected**.
- Docker running on the machine that executes the activities.
- A local Codex client, Claude Code, or a supported Claude Desktop installation.
- An internet connection for the first BusyBox image download.

The setup screenshots below come from real, isolated homeserver Desktop captures. The 1.0.12 setup verifies the complete administration catalog; this tutorial only needs **Operate workflows**. Your connection paths, tool count and instance names will differ. The workflow and execution screenshots show the separate homeserver demonstration made for this post.

The native setup and connector were tested with real MCP clients. These are AkôFlow screenshots, not screenshots of an authenticated Claude or Codex conversation. The prompts are instructions for you to run in your own AI app; wording and approval dialogs can vary between clients.

## 1. Enable MCP and choose an app

Open **Settings → MCP & AI apps**, then select **Enable MCP**.

![MCP settings with the service disabled before activation](/img/releases/v1.0.12/01-mcp-disabled.png)

Select **Add app**, choose your client and give the connection a recognizable name, such as `Codex — workflow learning`. Select **Operate workflows**, then **Create connection**.

![The app selector, connection name and permission choices in AkôFlow Desktop](/img/releases/v1.0.12/02-mcp-permissions.png)

The reference screenshot has **Full administration** selected to verify its complete catalog. For this walkthrough, select **Operate workflows** instead. **Read only** can inspect records but cannot create the workflow. Create a separate connection for each AI app so you can revoke one independently.

## 2. Install the generated client configuration

AkôFlow generates a local **stdio** connection. The AI app starts the bundled connector on the same computer as Desktop. Keep Desktop open while using it.

![The generated Codex configuration and its native installation action](/img/releases/v1.0.12/03-mcp-configuration.png)

Use the entry generated by your installation. The executable, helper and private connection-file paths in these screenshots belong to the documentation machine. Do not copy those paths into your own configuration.

### Codex

1. Select **Add to Codex** in the setup dialog.
2. Fully quit and reopen the app, then start a **new local chat**. For Codex CLI, start a new session.
3. In the CLI, use `/mcp` to check active servers. `codex mcp list` lists configured servers.

AkôFlow writes its entry into the local Codex configuration, preserving other servers. If you use a custom configuration location, use **Copy configuration** or **Open config** to merge the generated entry into the configuration your client actually loads. Codex supports local stdio servers through `config.toml`; see the [official Codex MCP documentation](https://developers.openai.com/codex/mcp).

### Claude Code

1. Choose **Claude Code** when creating the connection.
2. Select **Add to Claude Code** in its setup dialog.
3. Close the current Claude Code session and start a new one on this computer.
4. Use `/mcp` to inspect the connection.

AkôFlow installs a user-level stdio entry in `~/.claude.json`, preserving existing settings. For custom setups, use the generated entry and the [official Claude Code MCP guide](https://code.claude.com/docs/en/mcp).

### Claude Desktop

On macOS or Windows, choose **Claude Desktop** and select **Add to Claude Desktop**. For manual setup, use **Copy configuration**, open **Settings → Developer → Edit Config** in Claude Desktop, and merge the generated server into `mcpServers`. Preserve other entries. Fully quit and reopen Claude Desktop, then begin a new conversation.

![Claude Desktop configuration in the Linux reference installation, showing the manual copy flow](/img/interface/mcp/08-desktop-claude-configuration.png)

This Linux reference capture shows the copy-only fallback. Use the installation method that your AkôFlow setup dialog offers. The [local MCP setup guide](https://modelcontextprotocol.io/docs/develop/connect-local-servers) explains Claude Desktop's configuration and restart flow.

## 3. Verify both ends of the connection

In AkôFlow, select **Test MCP connection**. A successful test authenticates a real MCP client, discovers the tools permitted for this connection, and reads the daemon identity.

![A successful native MCP connection test in AkôFlow 1.0.12](/img/releases/v1.0.12/04-mcp-verified.png)

Now send this prompt in your AI app:

```text
Use the AkôFlow MCP tools to identify my connected AkôFlow instance
and list my workflows and available environments. If a list is empty,
tell me. Do not create or modify anything.
```

**Checkpoint:** the assistant makes an AkôFlow tool call and returns records from your instance, or an explicit empty list. An answer saying “I can help with AkôFlow” does not verify the connection. If it has no tools, reconnect its MCP server or restart the AI app.

The native test verifies the service. This first request verifies that **your AI app** loaded the server.

## 4. Ask for a concrete workflow

Start with a small experiment whose answer you know. Send:

```text
Use AkôFlow MCP to create a workflow named mcp-first-analysis in
namespace learning. First check whether that name already exists;
if it does, show it and do not overwrite it.

Use docker.io/library/busybox:1.36 with OCI delivery and sh -c.
Create three activities, each limited to 0.1 CPU and 32Mi memory:

1. prepare: write the values 2, 4 and 6, one per line, to measurements.txt.
2. analyze: depend on prepare, read measurements.txt, and use awk to
   write the arithmetic mean with two decimal places to mean.txt.
3. write-report: depend on analyze and write Mean: 4.00 to report.txt,
   deriving the value from mean.txt rather than hardcoding the answer.

Print each activity's output in its log and declare its output file
in expectedOutputs. Show the definition, create it through the MCP
tool, then read it back and return its workflow and version IDs.
Do not create a plan or start execution yet.
```

Open **Workflows → Definitions → mcp-first-analysis** in Desktop. The saved workflow must have three activities and two dependency arrows.

![The three-activity workflow created through MCP in the homeserver demonstration](/img/blog/mcp-first-workflow/workflow.png)

**Checkpoint:** compare the saved definition with the table. A chat response containing YAML is only a draft until the creation tool succeeds and readback confirms the record. Creating the definition does not execute it.

For an exact reference, [download the complete workflow YAML](/downloads/blog/mcp-first-workflow/mcp-first-analysis.yaml). It uses `command.executable.source` for the container image, `dependsOn` for ordering, and `expectedOutputs` for required files. AkôFlow stages a predecessor's workspace before its dependent activity starts. Each activity writes a different output filename.

## 5. Select where it will run

If you have no local environment yet, follow [Connect your local machine and create a scope](/blog/from-a-dag-to-your-first-run). Test the connection before saving the environment and confirm it is online. An execution scope selects the environment versions offered to planning.

Ask the assistant to discover those records:

```text
Use AkôFlow MCP to inspect mcp-first-analysis and list execution scopes,
their environments, resources, runtime bindings and connection health.
Find a scope with a healthy local execution runtime that supports OCI
containers. Return the exact persisted IDs and explain the selection.
Do not provision cloud resources or execute anything. If no suitable
scope exists, tell me what I need to configure in Desktop.
```

Then request the plan, replacing the bracketed text with the scope you reviewed:

```text
Create a manual plan for the saved version of mcp-first-analysis using
[my reviewed local scope]. Resolve IDs from the persisted records.
Assign all three activities to its local resource and execution runtime.
Use one second per activity as a planning estimate, preserve dependency
order, and save the plan through MCP. Read it back and return its ID,
assignments, runtime selection and execution mode. Do not execute yet.
```

Review the saved plan in Desktop. **One second is an estimate**, not a measured duration or timeout. The first image download may take longer. The homeserver demonstration used one local Docker resource; it did not allocate cloud machines or use simulation.

## 6. Execute once and wait for evidence

When the plan matches your intent, send:

```text
Start one real execution of the reviewed plan for mcp-first-analysis.
Use a unique run ID and return it as soon as submission succeeds.
Poll that run until it reaches a terminal state. Do not resubmit it
because it is pending or running. If it fails, inspect its activity
errors and report the cause before creating any replacement run.
```

Open **Workflows → Definitions → mcp-first-analysis → Plans**, open the selected plan, and open its execution. Wait for **completed** and **3/3** completed activities.

![The real homeserver execution completed all three activities](/img/blog/mcp-first-workflow/completed-run.png)

MCP submissions can return an operation or pending receipt before the work finishes. Submission success is not execution success. Keep the returned identifier and inspect that same operation or run instead of starting duplicates.

## 7. Read the result, not just the status

```text
Inspect the completed run using AkôFlow MCP. Report each activity's
status and exit code, inspect the final activity output and generated
files, and verify that report.txt contains Mean: 4.00. Include file
checksums when available and the workflow, plan and run IDs.
Distinguish files listed in metadata from file contents actually read.
If content cannot be retrieved, say so instead of inferring it.
```

In Desktop, open the run's **Activities**, select **write-report**, and open its activity detail page. Inspect **Activity output** and **Generated files**.

![The final activity output and generated files in the real demonstration](/img/blog/mcp-first-workflow/activity-output.png)

### Follow the data through the workflow

Open the run’s **Workspaces & data** tab. The activity/file graph connects each producer to its recorded output: `prepare` produces `measurements.txt`, `analyze` produces `mean.txt`, and `write-report` produces `report.txt`.

![The real run’s data graph links each activity to the file it generated](/img/blog/mcp-first-workflow/run-data.png)

Open **prepare** and scroll to **Activity output** to check the actual input values. The log prints `2`, `4` and `6`; the generated-file record identifies `measurements.txt` and its checksum.

![The prepare activity prints the input measurements and records measurements.txt with its checksum](/img/blog/mcp-first-workflow/prepare-data.png)

Open **analyze** to inspect the intermediate result. Its output is `4.00`, and its generated file is `mean.txt`.

![The analyze activity prints 4.00 and records mean.txt with its checksum](/img/blog/mcp-first-workflow/analyze-data.png)

Back in **Workspaces & data**, scroll to the recorded file locations and **Data transfers**. The demonstration records two workspace transfers totaling **17 bytes**. These transfers stage predecessor workspaces, so the second transfer includes the intermediate workspace’s files; its byte count is not just the size of `mean.txt`. Recorded locations describe execution evidence and may become unavailable after ephemeral workspaces are released.

![Recorded file locations and the two data transfers between the workflow activities](/img/blog/mcp-first-workflow/data-transfers.png)

The demonstration created `mcp-first-analysis`, saved `mcp-analysis-plan`, and executed `mcp-analysis-run`. The real run completed all three activities. Reading the final workspace file confirmed:

```text
Mean: 4.00
```

The workflow creation, planning, submission and status retrieval went through a real stdio MCP client on the homeserver. The final file contents were additionally checked directly in the isolated runtime workspace. [Download the observed verification record](/downloads/blog/mcp-first-workflow/observed-results.json).

## More prompts to try

Change one aspect at a time so you can explain the result.

**A new dataset:**

```text
Create a new workflow named mcp-analysis-10-20-30 using the same
three-stage structure, but with values 10, 20 and 30. Preserve the
original workflow. Show the changed commands and expected answer
before saving the new definition. Do not execute yet.
```

**Independent branches:**

```text
Draft a workflow that prepares measurements, computes the mean and
maximum in independent activities, then joins both into one report.
Show its DAG and file handoffs. Add dependencies only where a stage
needs its predecessor's files, and use distinct output filenames.
Explain whether my selected resource capacity permits parallel work.
Do not save or execute until I review the draft.
```

**Investigate a failure:**

```text
Inspect run [run ID] through AkôFlow MCP. Find the first failing
activity, quote the relevant error briefly, and distinguish an image,
connection, planning or command failure. Propose the smallest fix.
Do not change infrastructure or retry the run yet.
```

**Prepare a reproducibility summary:**

```text
Summarize run [run ID] using persisted AkôFlow records: workflow version,
container reference and resolved digest if recorded, scope, assignments,
activity outcomes, output paths and available checksums. Mark missing
evidence explicitly. Do not treat planned durations as measurements.
```

## When a step does not work

| Symptom                                                             | Next check                                                                         |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| AkôFlow verifies MCP but the assistant has no tools                 | Restart the client, start a new local session, and inspect its active MCP servers. |
| The assistant can list records but cannot create them               | Recreate its connection with **Operate workflows**.                                |
| Configuration points to another computer or an old application path | Generate it again from the Desktop installation on the client machine.             |
| No healthy local runtime appears                                    | Test the environment connection and inspect its resource/runtime binding.          |
| A run is pending                                                    | Inspect its operation and run events; keep polling the same ID.                    |
| The first activity cannot start                                     | Inspect its error and Docker/image availability before retrying.                   |
| `analyze` cannot find `measurements.txt`                            | Check the dependency, predecessor outcome and workspace-staging evidence.          |
| The run completes but the answer differs                            | Read the saved commands and actual files; verify the input values and formatting.  |

Use **Disable MCP** to pause connections, **Rotate credential** to replace a connection's credential, or **Revoke access** to remove one app's access. Reconnect the AI app after rotation. Keep secret values out of prompts and use the generated private references.

You now have a reusable pattern: describe a checkable experiment, save and inspect its definition, select a compatible execution scope, review a plan, execute once, and inspect the evidence.
